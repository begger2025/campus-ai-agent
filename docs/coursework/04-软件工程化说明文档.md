## 1. 引言

本文档回答评分标准中的两个问题：**自动化程度是否合理、协同方式是否合理**。

写作原则是"只写真实存在的"：每一项工程化手段都给出**载体**（脚本/配置/文档的仓库路径）与**实证**（运行数据、提交哈希、真实协作记录），评审可逐项复核。本项目的工程化不是为交作业补造的展品——第 5 章的成效数字（1600+ 用例 68 秒全量回归、两机并发采集零冲突、38 项缺陷全闭环）都来自开发过程的真实运行记录。

## 2. 自动化

### 2.1 数据管线自动化：从"八步人工"到"两条命令"

舆情数据管线原本需要人工执行 8 个环节（选词、改配置、逐平台爬取、四步处理脚本），现已收敛为**闭环两条命令**：

```
① 选题播种：python scripts/seed_crawl_queue.py --platform ks --from-recommendations --top 20
     智能选题（五路信号：用户提问/语料缺口/热点/新话题/贫瘠词降权）自动推荐关键词
     → 人工确认一次 → 播种进共享队列（dry-run 预览、防重复入队）
② 各机采集：python main.py --platform ks --from-queue yes     （多机自动认领，见 §3.3）
③ 一键管线：python scripts/run_pipeline.py
     同步 raw_posts → 清洗 processed_posts → 构建语义向量 → 生成舆情事件
```

`run_pipeline.py` 的工程细节（`backend/tests/test_run_pipeline.py` 9 用例覆盖编排逻辑）：

- **失败即停**：任一步骤非零退出，后续不跑，汇总表明确标注 `not-run`；
- **预览语义逐步映射**：`--dry-run` 翻译成各脚本各自的预览参数（sync/process 用 `--dry-run`、事件生成用 `--preview`、向量构建无预览语义则整步跳过并说明原因）；
- **防静默截断**：事件生成固定 `--limit 0` 全量分析（此前默认截断曾无声丢弃最旧 97 条帖子，见缺陷台账 DEF-D12）；
- 实测：全链路 dry-run 866 帖 → 125 事件预览 59 秒；终版语料全量 1257 帖 → 160 事件簇（第 3~7 轮爬取入库后实跑）。

管线各步骤自身全部**幂等可复跑**：建表 `IF NOT EXISTS`、导入按唯一约束去重、事件生成对齐跨轮记忆（事件 ID 稳定）。"重复执行零副作用"是所有管线脚本的硬性验收标准。

### 2.2 质量回归自动化：TDD + 一键回归 + CI

**测试驱动开发（TDD）**是全程执行的编码纪律：缺陷修复必须先写失败测试复现（红），再实现修复（绿），最后全量回归。台账中 38 项缺陷全部按此流程闭环。

**三套测试全部零网络依赖**（断网可跑，这也是 LLM 降级通道的常态化验证）：

| 套件 | 框架 | 规模 | 覆盖 |
|------|------|------|------|
| 主仓后端 | unittest | 1184 用例 | 接口/业务/算法/安全（SSRF 8 例、注入对抗）/竞态（409 语义） |
| 爬虫 | pytest | 198 用例 | 队列互斥/配额/去重/时间窗/平台一致性/贴吧登录校验与空结果分类/订阅增量刹车 |
| Agent 子仓 | unittest | 305 用例 | 核心算法/评测框架/记忆/ReAct |

**一键回归 `check.ps1`**：一条命令串起三套测试 + 前端构建，四步独立计时、不 fail-fast（一次看清所有红灯）、退出码=失败步数。实测全量 **68 秒**——"提交前必跑 check"因此成为可执行的纪律而非口号。

**持续集成**：`.github/workflows/ci.yml` 与 check.ps1 同口径（后端/爬虫/前端三任务），push 到 main 与 PR 自动触发；零密钥零外部服务依赖（得益于测试零网络设计）。已随仓库推送 GitHub 生效，PR #2（76 commits / 191 文件）触发 CI 三任务首跑。

### 2.3 AI 质量的自动化度量：基准 + 消融

本项目把"AI 效果"从主观感受变成**可自动复测的指标**——这是 AI 深度融合项目特有的工程化维度：

| 工具 | 用途 | 关键设计 |
|------|------|----------|
| `scripts/eval_chat_benchmark.py` | 26 题金标基准，四轴判分（意图路由/检索命中/引用合法/延迟） | 每轮结果 JSON 归档 docs/data/，跨版本可比对（基线 P50 13.4s → 终版 14.1s） |
| `scripts/eval_chat_dialogue.py` | 多轮对话评测（真实用户七轮对话回放） | 改路由提示词后必跑 |
| `scripts/ablation_*.py`（6 个） | 消融实验：精修/合并/风险/生命周期/时效/选题逐项开关对照 | 固定数据快照（SHA-256 锁定）+ temperature=0 + 响应缓存 ⇒ **任何人重跑同结果** |
| `scripts/check_question_coverage.py` | 真实问题清单覆盖率验收（目标 ≥80%） | 数据驱动的验收门 |

消融实验的典型产出：LLM 聚类精修使事件数 14→37、最大错误巨桶 91 帖→0、套话标题 14→0——**每一处 AI 的收益都有对照实验背书**，防止"为了用 AI 而用 AI"。

### 2.4 运维自动化

- **13 个幂等迁移/建表脚本**（加列、索引、建表均可复跑，线上执行一律"干跑→确认→执行→幂等复跑验证"四步纪律）；
- **冒烟闸门**：`smoke_backend.py --allow-mysql` 显式闸门防止误写共享库；
- **演示降级**：`make_demo_snapshot.py` 导出本地 SQLite 快照 + `demo.bat` 一键切换——共享云库抖动时演示不受影响；
- **一键启停**：run.bat（构建+启动）/ dev.bat（前后端联调）/ stop.bat。

### 2.5 容灾自动化

| 故障 | 自动化处置 |
|------|-----------|
| LLM 主通道（中转站 gpt-5.4）拥堵/欠费 | **备胎链自动切换**智谱 glm-5.2 直连：不可重试错误立刻切换；缓存整条链先查（备胎答过的秒回）；流式仅在首字前切换。8 个专项用例 + 端到端演练（坏主通道→备胎应答） |
| LLM 完全不可用 | 全部 9 处 AI 环节规则通道兜底，断网功能完整 |
| 采集机器掉线 | 队列租约超时自动回收任务，无需人工干预 |
| 共享 MySQL 不可达 | SQLite 快照降级 |
| 单条数据入库失败 | 逐条隔离，不中断整批（爬虫五平台一致性修复） |

### 2.6 自动化边界：有意保留人工的三处

工程判断力的另一面是**知道哪里不该自动化**：

1. **事件发布门**：LLM 只做"预审建议"（批量建议+理由+置信提示），发布决定永远在管理员——"静默错误答案是最坏缺陷"，AI 直接发布违背安全原则。为此我们把人工审核的**单次成本**自动化压缩：审核优先排序（风险>热度>时间）、AI 研判摘要进列表、批量操作逐条留痕；
2. **证据入库终审**：联网证据经三闸门（范围+核验+人审）才入库，机器采集、人来终审；
3. **平台登录态**：Cookie 过期需人扫码——平台风控决定的本质边界，如实标注而非伪装。

## 3. 协作化

### 3.1 代码协作：Git 工作流 + GitHub

**成文规范先行**（第 1 周即定稿 `docs/dev-guide.md`）：分支命名（`feat/ fix/ docs/ refactor/ chore/`）、Conventional Commits 提交格式、PR review 检查清单、敏感文件禁入库清单。规范在 220+ 次提交中实际执行——`git log --oneline` 即是证据，每条提交都是"type: 做了什么+为什么"的可读记录（如 `fix(security): 审计第2批 安全——证据核验 SSRF 防护`）。

**远端协作平台**（GitHub：begger2025/campus-ai-agent）：

- 分支管理：`main`（稳定主线）+ `feat/*`（功能分支）+ `archive/pre-v3-main`（历史版本归档留痕，体现项目演进）；
- **PR 流程实证**：PR #2「第二轮迭代」76 commits / 191 文件变更，创建即自动触发 CI 三任务检查，通过后合入 main——分支→PR→CI→Review→合并的完整闭环；
- 推送前执行**历史敏感信息审查**（.env 从未入库、cookie/key 历史零泄漏、登录态目录从未跟踪），这本身是协作安全的必要环节。

**凭据协作纪律**：真实凭据只存 `.env`（gitignore），仓库仅提供 `.env.example` 键名模板；爬虫登录态存本地浏览器目录不入库；共享库凭据通过 `docs/how-to-get-shared-mysql.md` 的安全流程分发。

### 3.2 契约协作：接口先行，两端并行

前后端/模块间以**契约文档**解耦并行开发：

| 契约 | 载体 | 作用 |
|------|------|------|
| 统一响应格式 | dev-guide §4：`{code, message, data}` + 错误码分段 | 前端一套拦截器处理全部接口 |
| API 契约 | `docs/api.md`（新增接口必须同步更新，写入 review 清单） | 前后端并行开发 |
| 依赖清单 | `docs/前端后端依赖事项.md` | 显式管理跨端阻塞项 |
| 页面职责 | `docs/page-responsibilities.md`（每页唯一的"数据层×动词"） | 消除四处重复的事件列表 |
| Agent 集成契约 | 子仓 `week2-integration-contract` 等 | 子仓算法与主仓产品的接口约定 |

### 3.3 数据协作：共享底座 + 多机协同采集（特色）

**共享 MySQL** 是团队协作的数据底座（工作包文档 work-package-0/1 定义接入流程与安全边界），成员各自开发环境连同一份真实数据，联调零同步成本。

**分布式协同采集**是本项目协作化的技术亮点——多台机器同时爬取而互不冲突：

- 任务队列表 `crawl_task_queue`：行级条件 UPDATE 抢占（`WHERE id=? AND status='pending'`，受影响行数==1 才算认领成功），**不依赖 MySQL 8.0 的 SKIP LOCKED**，5.7 即可保证互斥；
- 30 分钟租约：掉线机器的任务自动回收，其他机器接力；
- 配套三脚本（播种/监控/重置）+ 协同手册 `docs/machine-c-crawl-guide.md`（含排除法诊断流程，新成员照手册即可加入采集）；
- **真实并发实证**：两台机器（机器A/组员机）时间窗重叠并发采集，认领关键词零重叠、163 条入库数据零重复、队列终态干净——协同不是纸面设计，是跑过的。

### 3.4 跨仓协作：子仓孵化 → 白名单回移

Agent 算法在独立子仓（campus-opinion-agent）孵化验证，成熟后集成进主仓。两仓一致性由 `scripts/sync_opinion_core.py` 保证：

- **白名单制**：仅同步核心包 21 文件 + services 8 文件，同步范围显式受控；
- **dry-run 评审制**：先干跑输出 OVERWRITE 清单（相当于变更评审单），确认后 `--apply`，同步后必跑子仓全量回归（305 用例）；
- 自动改写导入前缀，两仓模块路径差异对代码透明；
- 子仓 20+ 次 sync 提交记录，两仓并存至今**零漂移事故**。

### 3.5 知识协作：文档体系 + 缺陷台账

- **80+ 篇过程文档**：周迭代验收（week2~week7）、爬取手册、交接文档、设计决策留档——成员轮换/多机协作时知识不随人走；
- **缺陷跟踪台账**（`docs/coursework/05a-缺陷跟踪台账.md`）：36 项真实缺陷按"严重级/根因/发现渠道/修复提交/回归验证"全量留档，含 5 项如实公开的已知限制；
- 复盘教训转化为流程约束（例：SQLite 测不出外键问题 → 约束类变更必须附生产语义专项用例）。
