## 2. 配置管理

### 2.1 配置与代码分离（三层配置模型）

```
第一层  .env（环境与密钥）      ── 不入库，每环境一份
   │
第二层  llm_config.py / config.py（运行时读取 + 默认值）
   │
第三层  功能开关（EVENT_*_ENABLED 等）── 按环节独立开关
```

- **第一层 `.env`**：数据库连接串、JWT 密钥、三组 LLM API key、管理员/演示账号密码、爬虫参数等。**绝不入库**（见 §2.3），仓库只提供 `.env.example` 键名模板。
- **第二层运行时配置**：`backend/services/llm_config.py` 集中读取环境变量并给出安全默认值（如 LLM 未配置时降级、超时/重试参数），代码不散读 `os.getenv`。
- **第三层功能开关**：`EVENT_REFINE_ENABLED`、`EVENT_RISK_ENABLED`、`EVENT_LIFECYCLE_ENABLED`、`EMBEDDING_ENABLED`、`LLM_HTTP_TRUST_ENV` 等——按环节独立开关，支撑**消融实验**与**故障隔离**（某个 AI 环节异常可单独关闭而不停服）。

**设计价值**：同一份代码通过不同 `.env` 即可在"本地 SQLite 演示 / 共享 MySQL 开发 / 公网部署"之间切换，零代码改动。

### 2.2 环境一致性与可复现

| 手段 | 载体 | 作用 |
|------|------|------|
| 依赖锁定 | `requirements.txt`（后端）、`package-lock.json`（前端） | 依赖版本可复现 |
| 环境隔离 | 三个独立 venv（根 / MediaCrawler / 子仓） | 依赖不串扰 |
| 键名模板 | `.env.example` | 新成员照抄即可配好环境 |
| 一键启停 | `run.bat` / `dev.bat` / `stop.bat` / `demo.bat` | 本地环境标准化 |
| 行尾规范 | `.gitattributes` | shell/服务文件强制 LF，防跨平台 CRLF 污染与线上 `bad interpreter` |
| 可选重依赖 | `sentence-transformers`（注释于 requirements） | 轻量档不装，自动规则降级 |

### 2.3 密钥与敏感信息管理（安全纪律）

**铁律：密钥永不入库。** 落实手段：

1. **`.gitignore` 拦截**：`.env`、`.venv/`、`data/*.db`、`data/cookies/`、`browser_data/`、`data/chat_memory.sqlite3`、`uploads/` 等全部忽略；
2. **只提交模板**：仓库含 `.env.example`（仅键名，值留空）；
3. **登录态本地化**：爬虫平台 Cookie 存本地浏览器数据目录，不进仓库；
4. **传输隔离**：部署时 `.env` 经 `scp` 单独传服务器，权限 `600`；
5. **历史审查**：推送 GitHub 前做过 git 历史敏感信息扫描（`.env` 从未入库、无 key/cookie 泄漏）；
6. **轮换计划**：3 个 API key（GLM/中转站/证据检索）与演示账号密码列入答辩后轮换清单。

> 运行态数据（LLM 缓存、会话记忆、事件记忆）也不入库——它们可由管线脚本重建，不构成单点。

## 3. 版本控制

### 3.1 工具与仓库

- **Git + GitHub**：仓库 `begger2025/campus-ai-agent`（私有）；截至终版 **237 次提交**。
- **分支策略**：

| 分支 | 用途 |
|------|------|
| `main` | 稳定主线，禁止直接 push，经 PR 合入 |
| `feat/*`、`fix/*` | 功能/修复分支（如 `feat/chat-latency-and-retrieval`） |
| `archive/pre-v3-main` | 历史版本归档，保留项目演进痕迹 |

### 3.2 提交规范（Conventional Commits）

全程执行 `<type>: <说明>` 格式（`feat/fix/docs/refactor/chore/test`），`git log --oneline` 即是可读的演化记录。示例：

```
fix(search): LIKE通配符转义6处 + 攻击面2输入边界对抗测试
feat(llm): 备胎链——主通道失败自动切 GLM 直连
docs(coursework): 交付物5 软件测试与质量保证报告
```

规范成文于 `docs/dev-guide.md`（第 1 周定稿），含分支命名、提交格式、文件命名、接口返回格式四项约定，在 237 次提交中实际执行。

### 3.3 协作流程（分支 → PR → 评审 → 合并）

```
拉功能分支 → 开发（TDD）→ 提交前跑 check.ps1 全量回归
  → push → 开 Pull Request → CI 自动检查 + 组员 review（dev-guide §6 清单）
  → 通过后合入 main
```

**实证**：PR #2「第二轮迭代」76 commits / 191 文件变更，创建即触发 CI 三任务，评审通过后合入——分支→PR→CI→评审→合并的完整闭环有真实记录。

### 3.4 跨仓版本一致性

Agent 算法在子仓（campus-opinion-agent）孵化，经 `scripts/sync_opinion_core.py` 白名单同步回主仓：dry-run 输出 OVERWRITE 清单（相当于变更评审单）→ 确认后 `--apply` → 子仓全量回归（305 用例）。两仓并存至今零漂移事故。

## 4. 持续集成（CI）

### 4.1 CI 流水线

`.github/workflows/ci.yml`，push 到 main 与 PR 自动触发，三个并行任务：

| 任务 | 内容 | 环境 |
|------|------|------|
| `backend-tests` | 后端 unittest（1183 用例） | Ubuntu + Python 3.11 |
| `crawler-tests` | 爬虫 pytest（181 用例） | Ubuntu + Python 3.11 |
| `frontend-build` | 前端 `npm run build` 构建校验 | Ubuntu + Node 20 |

**关键设计**：全部测试**零网络依赖、零密钥**（得益于测试零外部依赖纪律），CI 无需任何 secrets 即可运行——这也让 CI 配置本身不含任何敏感信息。

### 4.2 本地与远端同口径

| 层 | 工具 | 触发 |
|----|------|------|
| 本地提交前 | `check.ps1`（三套测试 + 前端构建，68 秒） | 开发者手动，作为提交纪律 |
| 远端 | GitHub Actions（同口径三任务） | push / PR 自动 |

本地与 CI 同口径，保证"本地绿=CI 绿"，避免环境差异导致的假通过。

### 4.3 质量门禁

- 提交前 `check.ps1` 必须全绿；
- PR 合入前 CI 三任务必须通过（可在 GitHub 设为分支保护强制项，列为运维路线图）；
- 涉及同步白名单文件的改动，回移子仓后须跑其 305 用例。

## 5. 部署

> §5.1~5.3 为部署**方案设计**；§5.4 为部署负责人实际完成并已上线的**部署实录**（全文见
> `docs/deploy-ecs.md`），两者的差异与取舍对照见 §5.4 表格。**当前线上地址：<http://8.134.250.107:9000>**。

### 5.1 部署方案总纲

**阿里云轻量应用服务器 + Nginx 反代 + systemd 托管 + 轻量档 + 同区连 RDS**。架构：

```
浏览器 ──HTTP──> [阿里云轻量服务器]
                  Nginx（唯一公网入口）
                  ├── /         → frontend/dist（静态，vue-router 兜底）
                  ├── /api/     → 反代 127.0.0.1:9000（uvicorn，仅本地监听）
                  └── /uploads/ → 反代 127.0.0.1:9000
                                     │
                              uvicorn（systemd 托管，单进程）
                              ├── 阿里云 RDS（同地域）
                              └── 出网 → 中转站 LLM / 智谱 GLM
```

**安全边界**：仅 Nginx 对公网开放；后端只监听 127.0.0.1；防火墙只开 80/22；RDS 白名单只加服务器 IP。

### 5.2 团队已备的部署资产

| 资产 | 作用 |
|------|------|
| `deploy/nginx-campus.conf` | Nginx 站点：静态前端 + `/api`、`/uploads` 反代 |
| `deploy/campus-backend.service` | systemd 托管 uvicorn（单进程、崩溃自愈、日志进 journald） |
| `deploy/deploy.sh` | 一键更新：拉代码→构建前端→装依赖→校验表→重启→健康检查 |
| `docs/deploy-runbook.md` | 部署操作手册（11 步 + 运维手册） |
| `scripts/deploy_to_ecs.ps1` | **实际使用**的一键更新脚本：本机 zip → scp 上传 → 保留远端 `.env` → 重启 → 健康检查 |
| `docs/deploy-ecs.md` | **实际部署实录**（部署负责人撰写：规格/环境/RDS 连接/踩坑与解决） |
| `.gitattributes` | 保证部署脚本以 LF 行尾入库，防线上执行报错 |

### 5.3 关键决策与现实约束

- **轻量档（不装 torch）**：核心 AI（对话/事件/风险/预审，走中转站 LLM）全部正常，仅语义补召回降级为字面搜索，省内存更稳；
- **裸 IP 直连 http**：境内服务器域名走 80/443 需 ICP 备案（周期数天），裸 IP 访问免备案，功能 100% 满足；HTTPS + 域名 + 备案列为运维路线图；
- **同区连 RDS**：服务器与 RDS 同地域，数据实时且消除抖动。

### 5.4 部署实录（已上线，全文见 `docs/deploy-ecs.md`）

**线上环境**：阿里云 ECS（Ubuntu 22.04，2 vCPU/2 GiB，华南3·广州）；uvicorn 监听
`0.0.0.0:9000` 同端口托管前端 `dist/` 与 `/api`；systemd 单元 `campus-ai` 常驻（崩溃自愈、
开机自启）；业务库连团队共享 RDS MySQL（ECS 公网 IP 已加白名单）。
访问地址 **<http://8.134.250.107:9000>**；上线验证含 `/api/ping` 数据源核对、SSH 断开存活、
演示账号全功能走查。后续更新用 `scripts/deploy_to_ecs.ps1` 一键完成（保留远端 `.env`）。

**方案（§5.1）vs 实际（§5.4）差异对照**——实际部署在时间与成本约束下做了合理简化：

| 项 | 方案设计 | 实际上线 | 差异评估 |
|----|----------|----------|----------|
| 公网入口 | Nginx 反代，后端仅监听 127.0.0.1 | 无 Nginx，uvicorn 直连 `0.0.0.0:9000` | 少一层转发、部署更简；代价是后端直接暴露公网。`deploy/` 的 Nginx 资产保留为升级路径 |
| 开放端口 | 80/22 | 9000/22 | 等价安全面（均为一个服务端口 + SSH） |
| RDS 连接 | 同地域内网 | 跨地域（ECS 广州 ↔ RDS 深圳侧），走 RDS 外网地址 + 白名单 | 有公网往返延迟，实测可用；同区迁移列入路线图 |
| Python | CI 基线 3.11 | 服务器 3.12（系统 3.10 过旧，PPA 安装） | 兼容矩阵内（3.11+） |
| 轻量档 | 不装 torch | 一致（语义补召回降级为字面搜索） | 与方案一致 |

两处已知风险及对策：演示口令与 JWT 密钥若仍为默认值，公网环境应按 `deploy/README.md`
的生产安全要求更换；RDS 白名单历史上存在 `0.0.0.0/0` 条目，应删除并仅保留 ECS IP（详见
`docs/deploy-ecs.md` §3.2）。踩坑记录（Windows 实例误选、scp 传 venv、`datetime.UTC` 版本
问题等 8 项）见实录 §8——失败与修正过程本身即部署经验的一部分。

## 6. 运维计划

### 6.1 监控与可观测性

| 维度 | 手段 |
|------|------|
| 进程健康 | `systemctl status campus-backend`；崩溃 systemd 自动重启 |
| 实时日志 | `journalctl -u campus-backend -f`（后端）、Nginx access/error log |
| 应用审计 | 三类审计日志（事件审核 / 管理员操作 / 系统日志）入库可查 |
| 任务留档 | crawl_tasks / evidence_runs / agent_run_logs 记录每次运行 |
| LLM 成本 | llm_client 用量追踪 + `/api/agent/public/usage` |
| 健康探针 | `GET /api/ping`（部署脚本自动校验） |

### 6.2 备份与恢复

- **数据库**：阿里云 RDS 自带自动备份；重要节点可 `mysqldump` 手动导出；
- **演示快照**：`scripts/make_demo_snapshot.py` 导出本地 SQLite，供离线演示与快速恢复；
- **配置**：Nginx/systemd 配置纳入 git（`deploy/`），可版本化回滚；
- **可重建数据**：向量文件、LLM 缓存、会话记忆均可由脚本重建，无需备份。

### 6.3 更新与回滚

- **更新**：`bash deploy/deploy.sh`（拉代码→构建→装依赖→幂等校验表→重启→健康检查，任一步失败即停）；
- **代码回滚**：`git checkout <上一个好版本> && bash deploy/deploy.sh`；
- **配置回滚**：`deploy/` 在 git 里，改坏 `git checkout` 复原。

### 6.4 降级预案（运维成熟度核心）

| 故障 | 自动/手动处置 |
|------|--------------|
| RDS 抖动/不可达 | 切 SQLite 演示快照（改 `.env` DATABASE_URL + 重启），演示不中断 |
| LLM 主通道故障 | **备胎链自动切换** gpt-5.4 → GLM，无需人工 |
| 单个 AI 环节异常 | 功能开关单独关闭该环节（`EVENT_*_ENABLED=false`），不停服 |
| 采集机器掉线 | 队列租约超时自动回收任务，其他机器接力 |
| 云部署整体故障 | 本地机 + 内网穿透（cpolar/frp）临时出公网址保底 |

### 6.5 故障响应流程

```
告警/发现（健康探针失败 / 用户反馈 / 日志异常）
  → 定位（journalctl 看后端、nginx log 看入口、verify_db_connection 查库）
  → 判断影响面 → 执行对应降级预案 → 修复根因 → 复盘登缺陷台账
```

### 6.6 容量与演进

- **当前容量**：单校数据 10³~10⁴ 帖量级，单进程 uvicorn + 2G 服务器足够；索引已就位（`scripts/add_indexes` 等）；
- **扩容路径**（运维路线图）：进程内状态（限流/会话/缓存）外置 Redis → uvicorn 多 worker → 语义检索演进 pgvector → 分支保护 + 覆盖率门禁 + Issues 看板。

### 6.7 安全运维检查清单

- [ ] `.env` 权限 600，不在 git
- [ ] 后端只监听 127.0.0.1，9000 未对公网放行
- [ ] 防火墙只开 80 + 22（22 限来源）
- [ ] RDS 白名单只加服务器 IP，未开 `0.0.0.0/0`
- [ ] 演示账号非弱口令；测试验收账号（wp8/wp9/smoke）已清理
- [ ] 答辩后轮换 3 个 API key
