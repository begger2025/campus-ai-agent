# 事件聚类的 LLM 精修（拆开误合并的大桶 + 具体化事件标题）

> 消融实验结果（真实数据、可复现）：[event-clustering-llm-refine-ablation.md](./event-clustering-llm-refine-ablation.md)
> 由 `python scripts/ablation_event_refine.py` 生成。

## 1. 这是在修什么缺陷

事件聚类原本是纯 embedding 的（`semantic_clustering.py`：贪心单趟 + 质心合并）。在 297 条
真实语料上，它产出一个 **91 帖的巨簇（占语料 31%）**，标题由「簇内词频 top-1」决定。
这个桶里装的是：

```
中山大学三大校区 哪个更好？ #升学规划
中山大学拟调整作息引争议！校方回应：已关注此事，会回应师生关切
吃饭，睡觉，骂校长，这都快成了中山学子的日常了！
中山大学副教授谈年轻人出路越来越少
第24期｜一天曝光一个神人学校——中山大学深圳校区
```

——校区选择、作息争议、吐槽、讲座、Vlog 全在一个"事件"里。两个结构性成因：

1. **每条帖子都含「中山大学」**，向量空间被这个共同词压平，子话题之间的夹角不够分开；
2. **标题 = 词频 top-1**，词频不理解语义。它抽中过噪声词「饭堂」（于是一个没有任何食堂帖的
   桶叫「饭堂相关讨论」），也从一份*物理*试卷里抽出过「压力」。

**调阈值治不了**：调低塌成 191 帖的巨桶，调高碎成 33 个重名事件。缺的不是阈值，是**对内容的
理解**——这正好是 LLM 会、embedding 不会的事。

代价是具体的：「中山大学作息调整」是这批语料里一个真实的校园争议（全语料 17 条相关帖），
纯 embedding 只把其中 10 条聚到一起、还有 3 条埋在那个 91 帖的巨桶里，而且事件名叫
「中山大学·中山大学作息调整相关讨论」。

## 2. 做法

把**够大的簇**的帖子标题交给 LLM，问它"这里面其实是几件事"，按它的划分把簇拆开，用它给的
标题。提示词里明令禁止「…相关讨论」这类套话标题，并**允许它说"这 N 条就是零散杂项"**——
不许为了好看硬把边角料塞进某个话题（gpt-5.4 本来就会这么做，这个诚实要保住）。

### 接缝在哪（依赖注入，核心包保持零依赖）

`backend/agent/public_opinion_core/` 不 import 任何 `backend.*`，能力一律**注入**。精修沿用
同一个模式（`service.py` 已有 `Embedder` / `SentimentClassifier`）：

| 层 | 文件 | 职责 |
| --- | --- | --- |
| 核心（stdlib-only） | `public_opinion_core/llm_refine.py` | 定义 `ClusterRefiner` 协议；**验证**模型输出；拆簇/合并/降级 |
| 核心 | `public_opinion_core/semantic_clustering.py` | 在"聚类之后、压制之前"调用精修 |
| 核心 | `public_opinion_core/service.py` | `cluster_refiner=None` ⇒ 跳过精修（与 embedder 同一口径） |
| 部署侧 | `backend/services/event_refiner.py` | 唯一读 `EVENT_LLM_*`、唯一发请求的地方；走 `call_llm` |
| 部署侧 | `backend/services/public_opinion_adapter.py` | 注入 `get_cluster_refiner()` |

`ClusterRefiner = Callable[[list[str]], Sequence[Mapping] | None]`：进去是一个簇的帖子标题
（规范顺序），出来是 `[{"title": ..., "members": [1-based 编号], "miscellaneous": bool}]`。
**`None` = 不精修，保留 embedding 的结果**——未配 key、关掉开关、答辩现场断网，流水线照跑。

### 精修哪些簇：`EVENT_REFINE_MIN_SIZE = 8`

- **下界是算术决定的**：一个簇要能拆出两个"公共事件"，至少得有 2 × `EVENT_MIN_CLUSTER_SIZE`
  （= 4）条帖子；再小的簇精修只能改名，不可能拆分。给 2 帖的簇打一次 LLM 调用是纯浪费。
- **8 落在真实分布的天然缺口上**：297 条语料的簇大小是 `91, 59, 24, 15, 13, 11, 10 | 7, 7, 6, 3, 3, 2, 2`，
  7 和 10 之间有个坎。取 8 选中 7 个簇、覆盖 **223/297 = 75%** 的语料，共 **7 次** LLM 调用。
  降到 4 要多花 4 次调用（+57%）去覆盖多出来的 26 条帖子（8.8%），而错标的严重程度是随簇
  变大而放大的（91 帖的桶里一条食堂帖都没有）。
- 代价（在消融报告里看得见）：小于 8 的簇保留词频标题，所以精修臂里仍剩 7 个「…相关讨论」。
  这是明码标价的成本取舍，`.env` 里 `EVENT_REFINE_MIN_SIZE` 可调。
- 上限 150 帖：更大的簇不精修（token 成本 + 编号越多模型越容易数错）。

### 同名话题跨簇合并

模型是**一簇一簇**看的，看不见别的簇。真实数据上两个 embedding 簇各自被认出「中大作息调整
争议」——同一件事本来就被切在两个簇里。标题相同的话题合成一个事件（质心按合并后的成员
重算），否则事件列表里又并排站着两个同名事件，和这次要修的缺陷是同一个毛病。

消歧规则同步改了一处：**LLM 标题撞车时绝不粘「相关讨论」的尾巴**（不然
「中大作息调整争议」会被消歧成「中大作息调整争议·中山大学相关讨论」，功能就白做了）。

## 3. 降级：模型可以失败，流水线不可以

**模型的输出在被信任之前，必须先对着真实的簇成员验一遍**（`llm_refine._validate_topics`）：

| 失败 | 处理 |
| --- | --- |
| 超时 / 网络 / SDK 抛异常 | 整簇作废，退回 embedding 的簇 + warning |
| 返回 `None` / 非列表 / 空列表 / 无法解析的 JSON | 同上 |
| **编造帖子编号**（簇里只有 8 条，却返回第 99 号） | 同上——绝不让幻觉重排真实数据 |
| **同一条帖子被塞进两个话题** | 同上（真实帖子不能被复制） |
| 空标题 / 非整数编号 | 同上 |
| **漏掉了几条帖子** | **不作废**：漏掉的原样留成一个残余簇。一条帖子都不许在精修中消失 |
| 一个簇也没精修成 | `clustering_mode` 如实记成 `semantic`（不是 `semantic+llm`），降级看得见 |

所有降级都进 `warnings` → `agent_run_logs`（`refined_clusters` 也记进 `output_summary`）。
`EVENT_MIN_CLUSTER_SIZE` 的语义不变：精修跑在压制**之前**，LLM 拆出的 1 帖话题照样不成事件。

失败路径全部有单元测试（`backend/tests/test_event_llm_refine.py`，零网络零数据库，注入假的
refiner）。

## 3.5 离群剔除：不属于这个事件的帖子，不许冒充它的证据

### 缺陷

已发布的事件「**东校区宿舍火灾**」有 4 条代表内容。三条是真实火情（2026-03-24 ~ 03-26），
第四条是：

```
快手 · #中大宿舍实拍 · @安好 · 2023-08-31 · 赞146
```

一张 **2023 年的宿舍照片，和火灾毫无关系**，却堂而皇之地站在事件的代表内容里。
embedding 之所以把它和火灾聚在一起，只是因为两边都写着「宿舍」。

**这不是模型能力问题**：把这 4 条标题原样交给模型问「每一条真的属于这个事件吗」，
`gpt-5.4` 和 `gpt-5.6-sol` 都答得又快又对（`1. 不属于 / 2. 属于 / 3. 属于 / 4. 属于`）。
**缺的是架构**：精修层只会问模型「这个簇里其实是几件事」，模型**无法表达"这条帖子哪个话题
都不属于"**——它要么把照片硬塞进某个话题，要么漏掉它，而漏掉的按既有契约是要
「原样保留为残余簇」的（丢真实数据比拆不干净更糟）。于是照片怎么都留在事件里。

后果不止于难看：事件的时间戳是从成员推出来的，这张照片把火灾事件的跨度从 **2 天撑到 938 天**
——正在做的时间衰减特性会被它彻底毁掉。

### 做法

模型的返回里多一个顶层 `unrelated` 数组：「这些帖子哪个话题都不属于」。
`event_refiner` 把它翻译成核心包认识的**剔除桶** `{"members": [...], "unrelated": true}`
（核心包的契约仍然只是"一串话题项"，没有开第二套机制）。被剔除的帖子：

- **各自单独成簇**，不带标题 → 一条孤零零的无关帖子不是"公共事件"，随即被**既有的**
  `EVENT_MIN_CLUSTER_SIZE` 压制掉（压制通道和压制计数都是现成的，没有新增旁路）；
- **剔除 ≠ 删除**：帖子仍在 `processed_posts` 里，仍计入情感统计与热度排行，
  它只是不再**冒充这个事件的证据**。

### 保守性：剔错一条，比留下一条更糟

留下一条边缘帖，读者自己看得出来；**剔掉一条真实成员，事件就丢了真实证据，而且丢得无声无息。**
两类错误不对称，所以剔除被设计成只能是"少数派修正"：

| 约束 | 值 | 为什么 |
| --- | --- | --- |
| **剔除上限** `EJECT_MAX_RATIO` | **1/3** | 簇是 embedding 按真实相似度聚出来的。模型的活是拂掉边缘污染（火灾簇里 1 张照片 = 4 选 1 = 25%），不是推翻聚类。一个模型说"这个簇里多数帖子都不属于这个簇"，它反对的是**聚类本身**，不是在指认离群点——此时正确动作是**退回 embedding 结果**（当前已发布、已知可用的行为），而不是让一次可能失灵的调用拆掉一个真实事件。剔 80% 的模型是坏了，不是有洞察。 |
| 越过上限 | **整份结果作废** | 不是"只剔前几条"——那等于承认了一个明显在胡说的输出。退回 embedding + warning。 |
| 提示词 | 明写「宁可留下一条不太确定的帖子，也不要剔错一条」 | 保守性写进 prompt，不只写在代码里。 |

**校验与对账**（和既有精修同一套，共用一个 `seen` 集合）：编号必须是这个簇里真实存在的成员；
一条帖子不可能既属于某个话题、又"哪个话题都不属于"；剔除 + 话题分配 + 残余簇必须对得上
真实成员表。任何一处对不上 ⇒ **整簇作废，保留 embedding 结果，记一条 warning**——
绝不让一个编造出来的编号去删掉一条真实帖子。模型只剔除、一个话题都不给 ⇒ 也算没干活，作废。

被剔除的帖子数进 `run_log.extra.ejected_notes`，并在 warning 里**指名道姓**列出剔走了哪几条，
既有的「压制」告警也会挑明其中有几条是离群剔除——**被移出事件的真实数据绝不允许无声消失**。

## 4. 确定性与成本

- `temperature=0`；调用走 `call_llm`，**重试 / JSON 响应缓存 / token 与耗时计费**都是现成的
  （`call_llm` 新增了 `model` / `api_key` / `base_url` 覆盖参数，模型名进缓存键——换模型
  必须换 key，否则会拿到另一个模型的旧答案）。
- 一次全量分析 = 7 次调用（约 9k token，43 秒）；缓存命中后为 0 元、秒回。
- 配置（`.env`，缺省回落到 `OPENAI_*`）：

```
EVENT_LLM_MODEL=gpt-5.4
EVENT_LLM_BASE_URL=...
EVENT_LLM_API_KEY=...
EVENT_REFINE_ENABLED=1      # 0 = 回到纯 embedding 聚类
EVENT_REFINE_MIN_SIZE=8     # 多大的簇才值得一次调用
```

## 5. 结果（详见消融报告）

| 指标 | 纯 embedding | + LLM 精修 |
| --- | --- | --- |
| 事件数 | 14 | 37 |
| 最大事件 | 91 帖（31% 语料） | 21 帖（7%） |
| 巨簇（> 20% 语料） | **1** | **0** |
| 「…相关讨论」套话标题 | 14 | 7 |
| 「作息调整」事件 | 「中山大学·中山大学作息调整相关讨论」11 帖 | **「中大作息调整争议」14 帖** |
| 　└ 捞回的作息帖 / 全语料 | 10 / 17 | **13 / 17** |
| 　└ 仍埋在巨簇里的作息帖 | 3 | **0** |

实验只跑 `data/fixtures/event_clustering_297.json`（297 条 `processed_posts` 的只读快照），
**不连数据库**：可复现、不给共用 MySQL 添负载。

## 6. 离群剔除的结果（`python scripts/ablation_event_refine.py`，三臂）

第二臂与第三臂共用**同一次模型输出**（`temperature=0` + 缓存），唯一差别是 `unrelated` 名单
**被无视**还是**被执行** —— 两臂之差干净地等于"离群剔除"这一个能力。

**缺陷复现（线上事件原样的 4 条成员 → 真实精修通道）**：

| | 帖数 | 时间跨度 |
| --- | ---: | ---: |
| 剔除前（线上现状） | 4 | **938 天**（2023-08-31 ~ 2026-03-26） |
| 剔除后「中大宿舍火情通报」 | **3** | **2 天**（2026-03-24 ~ 2026-03-26） |
| 被剔走的 `#中大宿舍实拍`（2023-08-31） | 1 | 单独成簇 → < `min_cluster_size` → 不成事件 |

**两个必须讲清楚的诚实结论：**

1. **这份 fixture 复现不出线上那个簇。** 同一批帖子在当前阈值下，那张照片被 embedding 分到了
   「零散杂项帖」，压根没进火灾簇（fixture 里的火灾事件是另外 4 条，跨度 42 天）。线上事件是
   另一批语料、另一次运行的产物。所以消融报告里单列了一节「缺陷复现」：把**线上事件原样的
   4 条成员**交给真实模型、走真实的精修通道（含编号校验与剔除上限），结果如上表——
   照片被剔除，跨度 938 天 → 2 天。
2. **全语料 297 条上，模型只剔了 1 条，且它没有改变任何一个已发布事件的成员。**
   被剔的是从 59 帖的「课程」簇里挑出来的
   「**台湾国立中山大学**有什么最值得选的课程推荐？」——**另一所同名大学**，剔得完全正确
   （这正是"词面像但不是一件事"的典型）。它没有改变事件列表，是因为在无剔除的那一臂里，
   模型本来就没把它分进任何话题，它落进了 1 帖的残余簇、同样被 `min_cluster_size` 压掉了。
   **本次实验中没有观察到误剔**（没有一条真实成员被剔走）。

结论：剔除能力在**它该起作用的地方**（线上那个火灾簇）确实起作用；在这份 fixture 上它保守到
几乎不动手——这正是设计要的方向（宁可不剔，不可剔错）。
