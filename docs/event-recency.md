# 事件时效性衰减（近期舆情优先，严重性不随时间打折）

> 消融实验结果（真实语料、可复现、不连数据库）：[event-recency-ablation.md](./event-recency-ablation.md)
> 由 `python scripts/ablation_event_recency.py` 生成。

## 1. 这是在修什么缺陷

平台的立身之本是**呈现近期校园舆情**。而改造前，整条流水线**时间盲**：热度是互动量的算术、
风险是 LLM 研判的严重性、排序是「风险等级 → ranking_score」——**没有任何一处看过
`publish_time`**。一条 2016 年的帖子和昨天的帖子，权重完全一样。

线上实测（2026-07-12，共享库）：已发布事件

| 事件 | risk_level | risk_score | 排名 | 成员帖发布于 |
| --- | --- | --- | --- | --- |
| **中大学生诽谤被开除** | high | 90.0 | **前三** | 两条都是 **2021-06-18（1849 天前）** |

评委点开首页第三条"当前校园舆情"，看到的是一桩**五年前**的处分。这一次点击就足以摧毁整个
平台的可信度——而系统对此一无所知，因为它从来没有问过"这件事是什么时候发生的"。

语料的年龄分布解释了它为什么能排上去（297 条帖子，全部有 `publish_time`）：

```
2016: 3   2017: 4   2018: 4   2019: 21  2020: 17  2021: 14
2022: 8   2023: 4   2024: 28  2025: 73  2026: 120
近 7 天: 6 条 (2%)   近 30 天: 12 条 (4%)   近 1 年: 152 条 (51%)
```

## 2. 为什么**不**叫 LLM

我们有精确的 `publish_time`。「这件事多老」是**减法**，「多老算旧」是**指数衰减**。

- LLM 更慢、更贵、不确定，而且**算术更差**。
- 更要命的是**它没法解释**。答辩时可以说：「这个事件的代表时间是 107 天前，半衰期 30 天，
  所以时效权重 = `0.5 ** (107/30)` = 0.084」——这站得住。说「模型觉得它不够新」——站不住。
- 该用 LLM 的地方已经在用了：**严重性研判**（`llm_risk`，判断"学校要不要立即处置"）和
  **离群剔除**（`llm_refine`，判断"这条帖子属不属于这个事件"）。那两处需要的是**判断**；
  这里需要的是**算术**。

## 3. 三根正交的轴

改造的核心是：**时效性是第三根轴，不是任何既有量的修饰符。**

| 轴 | 字段 | 谁算的 | 会不会被时间改写 |
| --- | --- | --- | --- |
| 严重性 | `risk_level` / `risk_score` | LLM 研判 | **不会**。宿舍火灾不会因为过了三个月就变得不严重。 |
| 流行度 | `heat_score` / `heat_rank` / `ranking_score` | 互动量的算术（实测事实，展示给用户） | **不会**。它是测量值，不是估计值。 |
| **时效性** | `event_time` / `age_days` / `recency_weight` / `priority_score` | **本次新增**：纯算术 | 它**就是**时间的函数。 |

排序键（`clustering.sort_events` 与 `api.sort_event_rows` 同一口径）：

```
priority = severity_weight(risk_level) × recency_weight
         = {low: 1, medium: 3, high: 9} × 0.5 ** (age_days / half_life)
```

两条性质是设计约束，不是巧合：

1. **权重全为 1 时（未标注 / 关掉衰减 / 全无时间戳），排序逐位退化回改造前的口径。**
   `severity_weight` 在 low<medium<high 上单调，所以它等价于原来的 `risk_rank`(3/2/1)，
   兜底链仍是 `ranking_score → heat_rank → heat_score`。老数据不会被打乱成随机顺序。
2. **足够旧的 high 会被今天的 low 压下去。** 衰减的动态范围（1 → 1e-6）远大于严重性的
   （1 → 9）。这不是副作用，**这就是要修的缺陷本身**。

## 4. 事件的代表时间：为什么取**中位数**而不是最新

一个事件有一堆成员帖，每条帖子有自己的 `publish_time`。取哪个当作"这件事发生的时间"？

- **`latest`（最新）**：只要有**一条**掉队的新帖——今天有人转发一句五年前的旧事、一条蹭话题
  的帖子被聚进来——整个事件就"变新"了。这恰恰是**最危险的失败模式**：它让**旧事件伪装成新
  事件**，而修这个缺陷的全部意义就是不让旧事件冒充新闻。
- **`median`（中位数）**：要**过半**成员帖是新的，事件才会前移。代价是一个**正在发酵**的事件
  会滞后——10 条帖子里 6 条是上周的，中位数就还停在上周，尽管今天又新增了 4 条。

**选 median**，因为两种错误的代价不对称：把正在发酵的事件晚一两天推上首页，损失的是一点及时性；
把五年前的处分当今天的新闻推上首页，损失的是整个平台的可信度。

消融实验里两种口径并排跑了，实测差距触目惊心（真实语料，摘录）：

| 事件 | 帖数 | 成员帖跨度 | median 年龄 | latest 年龄 |
| --- | ---: | ---: | ---: | ---: |
| 中大参观开放询问 | 2 | 2661 天 | **7.5 年前** | 2.7 个月前 |
| 中大校园与宿舍展示 | 31 | 2894 天 | **10.7 个月前** | 6 天前 |
| 中大课程与选课 | 15 | 3141 天 | **6.9 年前** | 1.0 年前 |

`latest` 会把一个跨度 7 年的话题桶报成"2.7 个月前"。

偶数个成员取**偏旧**的那个中位（`values[(n-1)//2]`）：宁可低估新鲜度，不可高估。

离群剔除（`b62abaa`）落地后成员表干净了很多（火灾事件跨度 938 天 → 42 天），中位数因此稳定
——但 `latest` 的劫持风险只是变小，没有消失（上表就是证据）。口径该守住还是守住。

`.env` 里 `EVENT_RECENCY_TIMESTAMP=latest` 可以切到最新口径（消融脚本两种都会打出来）。

## 5. 半衰期：为什么是 21 天

`EVENT_RECENCY_HALF_LIFE_DAYS`，默认 **21**（在建议区间 14–30 内取中）：

- **对着真实语料标定**：离群剔除之后，「东校区宿舍火情」这类真实事件的成员帖跨度是 **42 天**
  量级。半衰期取跨度的一半 ⇒ 一个**还在持续发帖**的事件在它的活跃期内始终保住 ≥ 0.5 的权重，
  不会被自己的"前半段"拖下去；而事件一停更，两三周就掉出首屏。
- **对着校园的信息周期**：校园议题以周为单位（课表、周考、周末）。14 天太短，一个仍在发酵的
  争议第二周就被腰斩两次；30 天太长，上个月的食堂投诉还能压住本周的新事。21 天 = 三周，
  一个议题从爆发、到学院回应、到被忘记的典型长度。
- **刻度**：7 天前 0.79 / 21 天前 0.50 / 42 天前 0.25 / 90 天前 0.05 / 一年前 6e-6。

`<= 0` 表示**关掉衰减**（消融对照臂、答辩现场断网/数据异常时的应急开关）。

**权重地板** `EVENT_RECENCY_MIN_WEIGHT`，默认 **1e-6**（≈ 20 个半衰期 ≈ 14 个月）：
这是**防下溢的护栏，不是语义阈值**。它保证 (a) 权重永远 > 0，陈旧事件之间的顺序不会因为整列
塌成 0.0 而变成随机；(b) 地板之下不再按年龄区分——14 个月前和 5 年前的事件，对一个"当前舆情"
看板来说是**同一种旧**，它们之间按严重性和热度排（这是有意义的区分，年龄不是）。
真想让年龄一路排到底：`EVENT_RECENCY_MIN_WEIGHT=0`（纯指数，实数下溢要 58 年才发生）。

## 6. 时间必须可注入

**任何纯函数里都不出现 `datetime.now()`。** `now` 一律由调用方在流水线/请求的**入口取一次**
再往下传参：

- `PublicOpinionAgentService.analyze_from_rows(..., now=...)`（缺省 `datetime.now(UTC)`，
  在入口取，不在深处取）
- `backend/routers/api.py::_now()` —— 每个请求取一次
- `scripts/ablation_event_recency.py --now 2026-07-12` —— 缺省用**语料最新帖的第二天**，
  所以消融报告是**永久可复现**的，而不是"今天跑出来碰巧是这样"

否则单测不可重复、消融不可复现、答辩现场的截图和当场重跑对不上。

## 7. 改了哪些调用点（以及**故意没改**哪些）

**改了：**

| 位置 | 改动 |
| --- | --- |
| `public_opinion_core/recency.py` | **新增**。纯算术、stdlib-only：代表时间、年龄、衰减、优先级、配置。 |
| `public_opinion_core/schemas.py` | `OpinionEvent` 增加 `event_time` / `age_days` / `recency_weight` / `priority_score` 四个**新**字段（不动任何既有字段）。 |
| `public_opinion_core/clustering.py` | `build_event_from_group` 算 `event_time`（规则/语义两条路径都经过它）；`sort_events` 的第一排序键改为 `severity × recency`。 |
| `public_opinion_core/service.py` | 收 `now` / `recency_half_life_days`；在**风险研判之后**盖时效性并重排；把半衰期与 now 记进 `agent_run_logs`。 |
| `public_opinion_core/payload_builder.py` | `date_range_json` 增加 `event_time`（**只落这个事实**）。 |
| `backend/routers/api.py` | **前端真正消费的那个顺序**：`GET /api/events` 改用 `sort_event_rows`（严重性 × 时效性），并在事件载荷里返回 `event_time` / `age_days` / `recency_weight` / `priority_score`；详情同。 |
| `backend/services/public_opinion_adapter.py` | 分析结果的 events 字典带上时效性四件套（preview / smoke 看得见）。 |
| `frontend/src/utils/age.js`（新）、`OpinionView.vue`、`EventDetailView.vue` | 把年龄**显示出来**：列表行「5.1 年前」（≥90 天标黄），详情页把原来误导性的「发布时间：{updated_at}」（其实是**分析写库时间**）改成「事件时间 + 距今」，分析时间另列。 |

**故意没改：**

| 位置 | 为什么不改 |
| --- | --- |
| `risk_level` / `risk_score`（`llm_risk`、`sentiment_risk`） | **严重性不随时间打折。** 宿舍火灾在事实层面就是严重的，过三个月不会变得不严重。严重性与时效性是两根**正交**的轴——上一轮工作刚把严重性从流行度里解耦出来，这一轮不能又把它和时间搅在一起。 |
| `heat_score`（存储值） | 它是**实测事实**，而且直接展示给用户（「热度 10.7 万」）。要衰减热度就另加派生量，绝不覆盖原值。本次没有任何地方需要衰减热度，所以一个派生量也没加。 |
| `heat_rank` / `ranking_score` | 平台内百分位与跨平台排序分，是热度的算术函数，同上。 |
| `sentiment_risk.py` 的帖子级风险 | 帖子级风险不进看板排序（事件才是 UI 上展示、管理员要处置的东西）。 |
| `admin_events.py`（管理端草稿列表，`ORDER BY created_at DESC`） | 那是**审核队列**，管理员要按"最近检出的先审"来处理，不是舆情看板。按发生时间排会让新检出的旧事件沉底、永远审不到。 |
| `opinion_chat_service._risk_sorted_events`（对话里"风险最高的事件"） | 用户问的是「哪些事件**风险最高**」——那是**严重性**问题，答案就该按严重性给。把时效性混进去会把一个明确的问题答成另一个问题。（对话里的事件本身仍然带 `event_time`，回答可以据实说明"该事件发生于 5 年前"。） |
| `public_events` 表结构 | **没有新增列**，也没有数据库迁移。`event_time` 塞进本来就装时间信息的 `date_range_json`；`age_days` / `recency_weight` **不落库**——它们是 `now` 的函数，冻进数据库第二天就是错的，由读侧用请求时刻现算。 |

## 9. 一个必须说清楚的问题：语料太旧了

**衰减修好了排序，但它修不了数据。** 看板衰减之后的 Top-3 是 **2.1 / 1.6 / 3.5 个月前**的事件
——**没有一条来自近 30 天**。原因很简单：近 30 天的帖子只有 12 条（4% 语料），而且分散在各个话题
里，凑不出一个近期事件。28 个事件里有 13 个的年龄超过 14 个月（触及权重地板）。

这是**数据问题，不是排序问题**，不能靠调参数掩盖：

- 调小半衰期只会让所有事件的权重一起变小，**相对顺序几乎不变**（都乘同一个指数），
  但会让"最新的"事件看起来也像陈旧的。
- 唯一的解法是**重新爬取**：把近 7–30 天的语料补上去（爬虫链路是现成的：
  `scripts/seed_crawl_queue.py` → `crawl.bat` → `scripts/process_raw_posts.py` →
  `scripts/generate_public_events.py`）。

在那之前，看板至少不再**撒谎**：每个事件都明写着「5.1 年前」，陈旧的标黄，五年前的处分不再
冒充今天的新闻排在第三。
